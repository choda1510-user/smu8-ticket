# sections 작업 규칙

## 역할
- `sections` 폴더는 여러 페이지나 레이아웃에서 재사용되는 화면 조각을 담당한다.
- 헤더, 사이드바, 검색 결과 탭, 페이지네이션처럼 페이지보다 작은 공통 UI를 둔다.
- 전체 페이지 레이아웃을 감싸는 구조는 `layouts`에 둔다.
- 특정 페이지에서만 쓰는 작은 UI는 우선 해당 페이지 파일 안에 둔다.

## 데이터와 상태
- `sections`는 가능한 한 props 또는 URL 상태를 받아 렌더링한다.
- 임시 더미 데이터나 고정 검색어를 컴포넌트 내부에 직접 선언하지 않는다.
- 서버 데이터 조회, JSON fetch, API 호출은 `sections`에서 직접 처리하지 않는다.
- 검색어, 현재 페이지, 선택 탭처럼 UI 동작에 필요한 최소 상태만 가질 수 있다.

## 라우팅
- 링크 이동은 `Link` 또는 `NavLink`를 사용한다.
- 사용자 이벤트로 경로를 조합해야 할 때만 `useNavigate`를 사용한다.
- URL 경로는 `App.tsx`에 정의된 라우트 구조를 따른다.
- 검색 관련 링크는 현재 query key를 일관되게 사용한다.

## 스타일
- 섹션별 CSS 파일이 이미 있는 경우 기존 `ComponentName.css` 패턴을 유지한다.
- className 기반 스타일을 우선 사용한다.
- 기존 클래스 이름과 레이아웃 구조를 불필요하게 바꾸지 않는다.

## 금지
- 페이지 전체 구조를 `sections`에 구현하지 않기
- 페이지별 비즈니스 로직을 `sections`에 넣지 않기
- API URL 또는 JSON 파일 경로를 `sections`에 직접 작성하지 않기
- 같은 헤더, 사이드바, 페이지네이션 UI를 페이지마다 중복 구현하지 않기

# layouts 작업 규칙

## 역할
- `layouts` 폴더는 라우트별 공통 화면 뼈대를 담당한다.
- `Outlet`을 기준으로 공통 UI와 페이지 본문 영역을 배치한다.
- 헤더, 사이드바, 검색 결과 메뉴 같은 공통 조각은 `sections`에서 가져와 조합한다.
- 실제 페이지 콘텐츠는 `pages`에서 렌더링한다.

## 구조
- 모든 layout 컴포넌트는 `Outlet`을 포함해야 한다.
- layout은 페이지 데이터를 직접 가져오지 않는다.
- layout은 라우팅 구조와 공통 배치만 담당한다.
- 중첩 라우트 구조는 `App.tsx`와 일치해야 한다.

## 데이터와 상태
- layout에서 fetch, API 호출, JSON 로딩을 하지 않는다.
- layout 내부 상태는 접힘/펼침, 메뉴 표시 여부 같은 레이아웃 UI 상태로 제한한다.
- 페이지별 선택값이나 상세 데이터는 `pages` 또는 `hooks`에서 처리한다.

## 스타일
- layout별 CSS 파일이 있는 경우 기존 `LayoutName.css` 패턴을 유지한다.
- 전체 폭, 본문 정렬, 사이드 영역 배치처럼 화면 골격에 해당하는 스타일만 layout CSS에 둔다.
- 버튼, 카드, 리스트 같은 페이지 내부 UI 스타일은 `pages` 또는 `sections`에서 관리한다.

## 금지
- layout에 페이지 전용 UI를 직접 구현하지 않기
- layout에서 API URL 또는 JSON 파일 경로를 직접 작성하지 않기
- layout에서 특정 페이지의 상세 데이터를 props 없이 하드코딩하지 않기
- `Outlet` 없이 단독 페이지처럼 작성하지 않기
